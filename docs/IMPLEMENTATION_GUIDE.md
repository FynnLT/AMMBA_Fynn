# AMMBA — Automated Market Maker for Batch Auctions
## Implementation Guide

---

## 1. System Overview

The AMMBA is a P2P energy market mechanism that runs as a **periodic batch auction**. Each market window (time slot) collects energy bids (buyers) and offers (sellers) in the off-chain DB. At market close, the clearing node calculates a uniform clearing price via a sigmoid function, allocates quantities pro-rata, and writes trade objects back to the off-chain DB. A smart contract on the Energy Web Chain (EVM) provides a transparent, auditable, on-chain anchor for the price calculation.

### Three Components

| Component | Type | Role |
|---|---|---|
| **AMM Smart Contract** | Solidity on Energy Web Chain (EVM) | On-chain sigmoid price calculation + audit anchor |
| **AMM Clearing Node** | Off-chain Python service | Fetches orders, runs matching, writes trades |
| **AMM Execution Node** | Off-chain Python service | Post-delivery penalty calculation (Phase 2) |

### Data Flow

```
Off-Chain DB ──► Clearing Node ──► Smart Contract (aggregated, anonymized)
                      │                     │
                      │◄── clearing_price ───┘
                      │
                      ├── preference allocation
                      ├── pro-rata quantity allocation
                      ├── ex-post energy-type multipliers
                      └──► write trades to Off-Chain DB

[After delivery]
Off-Chain DB ──► Execution Node ──► penalty calculation ──► write penalties to Off-Chain DB
```

## 3. AMM Smart Contract

### 3.1 Purpose

- Receives **anonymized, aggregated** inputs: total supply (kWh) and total demand (kWh) for a market slot
- Calculates the uniform clearing price on-chain using the sigmoid function
- Emits a `MarketCleared` event with the price
- Provides an immutable, verifiable audit record — individual orders are never submitted on-chain

### 3.2 Inputs / Outputs

**Scaling convention:** All energy and price values are stored as integers scaled by `10000` (matching the GSY DEX `NODE_FLOAT_SCALING_FACTOR`). E.g. `0.26 kWh` → `2600`, `28.5 ct/kWh` → `285000`.

**Call:** `clearMarket(market_id, community_uuid, time_slot, total_supply, total_demand, clearing_price)`

**State stored per call:**
- `bytes32 market_id` — blake2b-256 hash, same format as GSY DEX market IDs
- `bytes32 community_uuid`
- `uint256 time_slot`
- `uint256 total_supply` (kWh × 10000)
- `uint256 total_demand` (kWh × 10000)
- `uint256 clearing_price` (ct/kWh × 10000)
- `address caller`
- `uint256 timestamp`

**Event emitted:**
```solidity
event MarketCleared(
    bytes32 indexed market_id,
    bytes32 indexed community_uuid,
    uint256 time_slot,
    uint256 total_supply,
    uint256 total_demand,
    uint256 clearing_price,
    uint256 block_timestamp
);
```

### 3.3 Sigmoid Price Function

The clearing price is calculated as:

```
price = K_upper - (K_upper - K_lower) / (1 + exp(-B * (ratio - θ)))
```

Where:
- `ratio = total_supply / total_demand`
- `K_upper` = community retail buy price (ct/kWh) — passed as parameter
- `K_lower` = community feed-in tariff (ct/kWh) — passed as parameter
- `θ` (midpoint) and `B` (steepness) = community-specific sigmoid parameters (passed as parameters or set by owner)

**Edge cases:**
- If `total_demand == 0` or `total_supply == 0` → emit a no-trade event, return 0
- If `K_upper <= K_lower` → return `K_lower`

**Solidity implementation note:** EVM has no native floating point. Use fixed-point arithmetic (multiply by 1e6 or 1e18). The sigmoid `exp()` must be approximated (e.g. via ABDK Math 64.64 library or a polynomial approximation). Alternatively, run sigmoid off-chain in the Clearing Node and have the contract only verify and store the result with the inputs for audit — this is simpler and avoids precision issues.

> **Recommended approach:** Run the sigmoid computation off-chain. The contract receives `(total_supply, total_demand, clearing_price)`, verifies that the price is within `[K_lower, K_upper]`, and records all inputs + the price for audit. This avoids expensive/complex on-chain floating-point math.

### 3.4 Access Control

- Only a whitelisted `CLEARING_NODE_ADDRESS` can call `clearMarket`
- Owner can update sigmoid parameters `(theta, B)` and price bounds `(K_upper, K_lower)` per community

### 3.5 Contract Interface

```solidity
// All uint256 values are scaled × 10000 (NODE_FLOAT_SCALING_FACTOR)
interface IAMMContract {
    function clearMarket(
        bytes32 market_id,
        bytes32 community_uuid,
        uint256 time_slot,
        uint256 total_supply,       // kWh × 10000
        uint256 total_demand,       // kWh × 10000
        uint256 clearing_price      // ct/kWh × 10000 (computed off-chain)
    ) external returns (bool);

    function setCommunityParams(
        bytes32 community_uuid,
        uint256 k_upper,            // ct/kWh × 10000
        uint256 k_lower,            // ct/kWh × 10000
        uint256 theta,              // × 10000
        uint256 steepness           // × 10000
    ) external onlyOwner;

    function getClearingResult(bytes32 market_id) external view
        returns (uint256 time_slot, uint256 supply, uint256 demand, uint256 price);
}
```

## 4. AMM Clearing Node

### 4.1 Purpose

The Clearing Node is an off-chain Python service that orchestrates each market clearing cycle:

1. Receive trigger from Market Orchestrator
2. Fetch open orders for the closing market slot
3. Aggregate supply and demand
4. Compute clearing price using sigmoid
5. Call the AMM Smart Contract (records clearing on-chain)
6. Apply user preference allocation (Phase 2)
7. Compute pro-rata quantity allocations
8. Generate and POST trade objects to the Off-Chain DB
9. Update order statuses to `Executed`

### 4.2 Trigger Interface

The Clearing Node exposes a lightweight HTTP endpoint. The Market Orchestrator calls it when a market slot closes:

```
POST /trigger-clearing
{
  "market_id": "market1",
  "community_uuid": "communityid_1",
  "time_slot": 123123
}
```

The Clearing Node responds immediately with `202 Accepted` and processes asynchronously (or synchronously if the clearing is fast enough).

### 4.4 Clearing Algorithm

#### Step 1: Fetch Open Orders

```
GET /orders?market_id={market_id}&start_time={time_slot}&end_time={time_slot + TIME_SLOT_SEC}
```

The `start_time` / `end_time` filter maps to the `time_slot` range for this delivery window. Filter results client-side: `status == "Open"`, then split by `order_type` into `bids` (buyers) and `offers` (sellers).

Orders with `status != "Open"` (Executed, Expired, Deleted) must be excluded — they have already been settled or cancelled.

#### Step 2: Aggregate

```python
total_supply_kwh = sum(o["energy"] for o in offers)
total_demand_kwh = sum(b["energy"] for b in bids)
```

If either is zero → no trade for this slot, mark all orders `Expired`, return.

#### Step 3: Compute Clearing Price

```python
ratio = total_supply_kwh / total_demand_kwh

def sigmoid_price(ratio, k_upper, k_lower, theta, B):
    if k_upper <= k_lower:
        return k_lower
    return k_upper - (k_upper - k_lower) / (1 + math.exp(-B * (ratio - theta)))

clearing_price = sigmoid_price(ratio, k_upper, k_lower, theta, B)
```

Clamp: `clearing_price = max(k_lower, min(k_upper, clearing_price))`

#### Step 4: Record On-Chain

Scale values before calling the contract:
```python
supply_scaled  = to_node_int(total_supply_kwh)
demand_scaled  = to_node_int(total_demand_kwh)
price_scaled   = to_node_int(clearing_price)
```

Call `contract.clearMarket(market_id_bytes32, community_uuid_bytes32, time_slot, supply_scaled, demand_scaled, price_scaled)`. Wait for transaction confirmation. Save the `tx_hash`.

`market_id` is already a hex hash string from the trigger payload — convert to `bytes32` via `bytes.fromhex(market_id.lstrip("0x"))`.

#### Step 5: Compute Traded Quantity and Pro-Rata Allocations

```python
traded_quantity = min(total_supply_kwh, total_demand_kwh)

# Each seller's allocated energy
for offer in offers:
    offer["allocated_energy"] = (offer["energy"] / total_supply_kwh) * traded_quantity

# Each buyer's allocated energy
for bid in bids:
    bid["allocated_energy"] = (bid["energy"] / total_demand_kwh) * traded_quantity
```

#### Step 6: User Preference Allocation (Phase 2 — implement after preferences API is available)

Once `requirements` / `attributes` are embedded in orders:

1. **Preferred Trading Partner priority:** Identify mutual pairs (buyer A listed seller B, seller B listed buyer A). Allocate their quantities first at the clearing price, up to their demanded/offered volumes.
2. **Residual pool:** Remaining unfilled volume is distributed pro-rata to all remaining participants.
3. **Energy type multipliers:** Fetched from off-chain DB (community manager submits them). Applied ex-post to the clearing price per trade:
   - Green energy trades: `final_price = clearing_price * (1 + green_multiplier)`
   - Grey energy trades: `final_price = clearing_price * (1 - grey_levy)`, capped at `levy_cap`
   - Dynamic subsidy scaling if grey revenue is insufficient

#### Step 7: Generate Trade Objects

For each matched (buyer, seller) pair, create **two trade objects** using the pool as intermediary:

**Hashing orders (matching GSY DEX convention):**
```python
import hashlib, json

def blake2b_hash(data: dict) -> str:
    """Produces a blake2b-256 hex hash of a JSON-serialised dict (sorted keys)."""
    encoded = json.dumps(data, sort_keys=True).encode("utf-8")
    h = hashlib.new("blake2b", encoded, digest_size=32)
    return "0x" + h.hexdigest()
```

**Trade A: Buyer → Pool**
```python
trade_uuid = str(uuid4())
trade_a = {
  "_id": blake2b_hash({...trade_a_contents...}),
  "trade_uuid": trade_uuid,
  "status": "Settled",
  "buyer": bid["created_by"],
  "seller": pool_id,                 # e.g. "AMM_POOL_communityid_1"
  "market_id": market_id,
  "time_slot": time_slot,
  "creation_time": int(time.time()),
  "bid": {
    "buyer": bid["created_by"],
    "nonce": bid.get("nonce", 1),
    "bid_component": {
      "area_uuid": bid["area_uuid"],
      "market_id": bid["market_id"],
      "time_slot": bid["time_slot"],
      "creation_time": bid["creation_time"],
      "energy": bid["allocated_energy"],
      "energy_rate": clearing_price
    }
  },
  "bid_hash": bid["order_id"],       # order_id IS the blake2b hash in GSY DEX
  "offer": {
    "seller": pool_id,
    "offer_component": {
      "area_uuid": pool_id,
      "market_id": market_id,
      "time_slot": time_slot,
      "creation_time": int(time.time()),
      "energy": bid["allocated_energy"],
      "energy_rate": clearing_price
    }
```

In the AMM, every buyer trades with the pool and every seller trades with the pool. This means you generate `len(bids) + len(offers)` trade objects (one per participant).

#### Step 8: POST Trades and Update Orders

```
POST /trades-normalized   [list of all trade objects]
```

In the GSY DEX, order status updates (`Executed`, `Deleted`) are driven by the event listener on the orderbook service — it subscribes to blockchain events (`OrderExecuted`, `OrderDeleted`) and updates statuses automatically. Since our EVM contract emits a `MarketCleared` event (not per-order events), the Clearing Node must update order statuses directly after the trade POST succeeds.

Coordinate with Spyros on whether a `PATCH /orders/{id}` endpoint exists. If not, post a new order object with the updated status. Fully matched orders → `Executed`. Partially matched orders → leave `Open` with energy reduced to the residual amount (or mark `Executed` and let the residual create a new order — TBD).

### 4.7 Error Handling

- If the on-chain transaction fails: do not write trades, log the error, allow retry on re-trigger
- If the off-chain DB is unreachable: fail fast, alert
- If clearing produces a price outside `[K_lower, K_upper]`: clamp and log a warning
- All clearing runs must be idempotent — check whether trades already exist for this `market_id` + `time_slot` before proceeding

## 5. AMM Execution Node

> **Phase 2 — to be implemented after energy delivery infrastructure is ready.**

### 5.1 Purpose

After the energy delivery period ends, the Execution Node:

1. Fetches settled trades and post-delivery measurements from the Off-Chain DB
2. Calculates penalties for deviations between what was traded and what was actually delivered
3. Posts penalty results back to the Off-Chain DB (and optionally to GSY DEX / BLODO)

### 5.2 Trigger

The Execution Node runs as a **polling loop** (same pattern as the GSY DEX execution engine):

```python
async def main():
    while True:
        previous_slot = compute_previous_timeslot(TIME_SLOT_SEC, EXECUTION_OFFSET_MIN)
        await run_execution_cycle(offchain_db_url, previous_slot)
        await asyncio.sleep(polling_interval_sec)
```

`EXECUTION_OFFSET_MIN` (default `-120` in GSY DEX, i.e. 2 hours after delivery start) controls when the Execution Node considers a delivery window closed and measurements available. This avoids needing the Market Orchestrator to send an explicit trigger.

`compute_previous_timeslot` rounds the current time back to the most recently completed slot that is older than `|EXECUTION_OFFSET_MIN|` minutes.

### 5.3 Penalty Formulas

From the simulation specification, three penalty types apply:

#### Seller Shortfall Penalty (Φ_t,j)

Applied when a seller's actual delivered energy is less than what they traded:

```
Φ_t,j = K_sho * max(0, energy_traded_j - actual_delivered_j - η)
K_sho = γ * K_upper       (γ > 1, e.g. 1.1)
η = tolerance threshold   (e.g. 0.0 initially)
```

`actual_delivered_j` comes from post-delivery smart meter measurements (`GET /asset_measurements`).

#### Seller Externality Penalty (supply-limited rounds)

Applied when a seller withheld supply, raising the price for all buyers (VCG mechanism):

```
W_sell_j = max(0, actual_deliverable_j - energy_traded_j - η)

For each seller j where W_sell_j > 0:
  counterfactual_supply = total_supply + W_sell_j
  counterfactual_ratio = counterfactual_supply / total_demand
  p_counterfactual = sigmoid_price(counterfactual_ratio, ...)
  externality_penalty_j = max(0, (clearing_price - p_counterfactual) * traded_quantity)
```

#### Buyer Externality Penalty (demand-limited rounds)

Applied when a buyer underfunded/underreported demand, reducing price for all sellers:

```
W_buy_i = max(0, actual_demand_i - reported_demand_i)

For each buyer i where W_buy_i > 0:
  counterfactual_demand = total_demand + W_buy_i
  counterfactual_ratio = total_supply / counterfactual_demand
  p_counterfactual = sigmoid_price(counterfactual_ratio, ...)
  externality_penalty_i = max(0, (p_counterfactual - clearing_price) * traded_quantity)
```

### 5.4 Data Requirements

To compute penalties, the Execution Node needs:
- The clearing result: `total_supply`, `total_demand`, `clearing_price`, `traded_quantity`, per-agent allocations — all recoverable from trade objects via `GET /trades?market_id={id}`
- Sigmoid parameters (`theta`, `steepness`, `k_upper`, `k_lower`) for counterfactual price calculations — stored in `parameters` of each trade object (see Section 2 trade schema)
- Post-delivery measurements: actual energy injected/consumed per `area_uuid` for the `time_slot` — from `GET /asset_measurements`

The decision to embed sigmoid params in the `parameters` field of each trade (rather than a separate lookup) means the Execution Node is fully self-contained from the trade objects alone.

### 5.5 Output

Penalty results are written back to the Off-Chain DB. Exact schema TBD with Spyros — likely the `parameters` field of the trade object is extended, or a separate `/penalties` endpoint is used.

## 8. Market Timing Reference

From GSY DEX constants (configurable via env vars):

| Parameter | Default | Meaning |
|---|---|---|
| `TIME_SLOT_SEC` | 900 | 15-minute delivery slots |
| `SPOT_MARKET_OPEN_OFFSET_MIN` | -180 | Market opens 3h before delivery |
| `SPOT_MARKET_CLOSE_OFFSET_MIN` | -60 | Market closes 1h before delivery → **AMM clearing runs here** |
| `EXECUTION_OFFSET_MIN` | -120 | Execution Node runs 2h after delivery start |

**Example timeline for a 14:00 delivery slot:**

```
10:00  →  spot market opens (users can submit orders)
13:00  →  spot market closes → Market Orchestrator triggers AMM Clearing Node
13:00  →  Clearing Node: fetch orders, compute price, call contract, write trades
14:00  →  energy delivery begins
16:00  →  Execution Node: fetch measurements, compute penalties
```

The Clearing Node does not need to know about market open/close times — it simply responds to the trigger from the Market Orchestrator.
